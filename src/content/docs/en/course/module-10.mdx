Welcome to Module 10. You've built POMs, fixtures, API tests, and CI pipelines. Now we tackle the single biggest performance bottleneck in a real test suite: **logging in before every test**.

By the end of this module you'll log in **once**, reuse that authenticated state across your entire suite, and understand exactly which reuse technique fits which kind of app — including the one our practice app actually needs.

## Why logging in every test is slow and brittle

Most test suites start with a `beforeEach` that navigates to the login page, fills credentials, and submits the form. It feels safe and predictable. In practice it creates two serious problems.

**The time problem.** A typical UI login takes 1–3 seconds. Multiply that by 50 tests and you lose 2–3 minutes per run before a single assertion fires. At 200 tests the overhead exceeds 10 minutes.

**The flakiness problem.** Every login attempt crosses the network, fills form fields, waits for redirects, and depends on the server responding within a tight timeout. Each of those steps can fail independently. A flaky login is not a test bug — it looks like one, though, and every debug session traces back to the same place.

Playwright gives us two ways to avoid repeating login: **`storageState`** (serialise the authenticated state to disk and replay it) and **an authenticated fixture** (log in once inside a reusable browser context and hand the logged-in page to every test). This module teaches both, and — crucially — when each one works.

---

## The `storageState` concept

When a user logs in through a browser, the server sends back proof of identity — typically one or more of these:

- A **session cookie** set via the `Set-Cookie` response header
- A **JWT token** stored in `localStorage` or a non-HTTP-only cookie
- A combination of both

Playwright's `storageState` serialises that proof into a single JSON file with two top-level keys:

```json
{
  "cookies": [
    {
      "name": "session",
      "value": "abc123...",
      "domain": "localhost",
      "path": "/"
    }
  ],
  "origins": [
    {
      "origin": "http://localhost:3000",
      "localStorage": [
        { "name": "token", "value": "eyJhbGciOi..." }
      ]
    }
  ]
}
```

**Saving state** is done after a successful login:

```ts
await page.context().storageState({ path: 'auth/customer.json' });
```

Note the call is on `page.context()`, not on `page` — `storageState` is a `BrowserContext` method.

**Loading state** is done when you create a new context (or through config, which does it automatically):

```ts
const context = await browser.newContext({
  storageState: 'auth/customer.json',
});
```

Before any page loads in that context, Playwright pre-populates cookies and localStorage from the file. The app sees an already-authenticated browser.

**When `storageState` is the perfect tool.** It shines when authentication lives somewhere it can capture:

- A **JWT (or any token) in `localStorage`** — captured via the `origins` key
- A **non-HTTP-only cookie** — one that JavaScript can read through `document.cookie`

Most token-based SPAs fall into this category, and for them the classic "log in once, save `storageState`, reuse it everywhere" pattern is exactly right.

---

## The catch: HTTP-only session cookies

`storageState` can only save what the page can read: cookies exposed to `document.cookie` plus `localStorage`/`sessionStorage`. It **cannot** capture a cookie marked `HttpOnly`, because the browser deliberately hides those from JavaScript.

This matters for our practice app. **TestMarket Lab authenticates with a server-side session.** It uses `express-session`, whose cookie (`connect.sid`) is **HTTP-only** by default. There is no JWT, and the login response carries no token — `POST /api/auth/login` returns only `{ id, email, name, role }`.

The consequence is direct: if you log in and then call `page.context().storageState({ path })`, the resulting file **will not contain the session cookie**. Reload that state in a fresh context and the app treats you as logged out. The "save `storageState` once" recipe simply does not carry the session for an app like this.

> The fix is **not** to make the cookie non-HTTP-only — that would weaken the app's security to suit the tests. The fix is to use a pattern that keeps the live, HTTP-only cookie inside a real browser context: an **authenticated fixture**.

So for the rest of this module: learn `storageState` as the right tool for token/localStorage auth (you *will* meet those apps), but use the **fixture-login** approach for every TestMarket Lab exercise.

## The authenticated-fixture pattern (what our app needs)

The idea is simple: perform the login **once** inside a `BrowserContext`, then hand that already-authenticated context (and its page) to each test through a fixture. The HTTP-only session cookie lives inside that context the whole time — we never try to serialise it, so the `HttpOnly` flag is irrelevant.

```ts
// fixtures/auth.fixture.ts
import { test as base } from '@playwright/test';
import type { Page } from '@playwright/test';

async function login(page: Page, email: string, password: string) {
  await page.goto('/auth/login');
  await page.fill('#email', email);
  await page.fill('#password', password);
  await page.click('#login-btn');
  // The server redirects after login and shows a success flash.
  await page.waitForURL((url) => !url.pathname.startsWith('/auth/login'));
}

type AuthFixtures = {
  customerPage: Page;
  adminPage: Page;
};

export const test = base.extend<AuthFixtures>({
  customerPage: async ({ browser }, use) => {
    const context = await browser.newContext();
    const page = await context.newPage();
    await login(page, 'customer@test.io', 'customer123');
    await use(page);
    await context.close();
  },

  adminPage: async ({ browser }, use) => {
    const context = await browser.newContext();
    const page = await context.newPage();
    await login(page, 'admin@test.io', 'admin123');
    await use(page);
    await context.close();
  },
});
```

Usage in a test — no login code, just ask for the role you need:

```ts
import { test } from '../fixtures/auth.fixture';
import { expect } from '@playwright/test';

test('logged-in customer sees the profile link', async ({ customerPage }) => {
  await customerPage.goto('/');
  await expect(customerPage.locator('[data-testid="nav-profile"]')).toBeVisible();
});

test('admin can reach the admin panel', async ({ adminPage }) => {
  await adminPage.goto('/admin');
  await expect(adminPage.locator('h1')).toContainText('Admin');
});

test('customer cannot reach the admin panel', async ({ customerPage }) => {
  await customerPage.goto('/admin');
  // No /unauthorized route — the app redirects non-admins to home with a flash error.
  await expect(customerPage).toHaveURL('/');
  await expect(customerPage.locator('[data-testid="flash-error"]')).toBeVisible();
});
```

Each fixture is **test-scoped** here: it creates a fresh context per test that needs it. That is clean and isolated, but it does log in once per test. The next section shows how to amortise the login cost across a whole worker.

### Worker-scoped login (log in once per worker)

If you have many tests that all need the same role, pay the login cost once **per worker** instead of once per test. Mark the fixture `{ scope: 'worker' }` and reuse its context:

```ts
// fixtures/auth.fixture.ts
import { test as base } from '@playwright/test';
import type { Page, BrowserContext } from '@playwright/test';

type WorkerAuthFixtures = {
  customerContext: BrowserContext;
};
type TestAuthFixtures = {
  customerPage: Page;
};

export const test = base.extend<TestAuthFixtures, WorkerAuthFixtures>({
  // One logged-in context per worker process.
  customerContext: [async ({ browser }, use) => {
    const context = await browser.newContext();
    const page = await context.newPage();
    await page.goto('/auth/login');
    await page.fill('#email', 'customer@test.io');
    await page.fill('#password', 'customer123');
    await page.click('#login-btn');
    await page.waitForURL((url) => !url.pathname.startsWith('/auth/login'));
    await page.close();
    await use(context);
    await context.close();
  }, { scope: 'worker' }],

  // A fresh page in the shared authenticated context for each test.
  customerPage: async ({ customerContext }, use) => {
    const page = await customerContext.newPage();
    await use(page);
    await page.close();
  },
});
```

Tests written against `customerPage` look identical to before — they just no longer pay a login per test. The session cookie stays alive inside the shared worker context for the whole worker's lifetime.

## A note on `globalSetup` and setup projects

You will see two other ways to "log in once" in Playwright docs and other suites: a `globalSetup` function, and a dedicated **setup project** that other projects declare via `dependencies`. Both run a login step once and then point `use.storageState` at the saved file:

```ts
// playwright.config.ts (storageState-based — works for TOKEN/localStorage apps)
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  projects: [
    { name: 'setup', testMatch: /auth\.setup\.ts/ },
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'], storageState: 'auth/customer.json' },
      dependencies: ['setup'],
    },
  ],
});
```

```ts
// tests/setup/auth.setup.ts
import { test as setup, expect } from '@playwright/test';

setup('authenticate as customer', async ({ page }) => {
  await page.goto('/auth/login');
  await page.fill('#email', 'customer@test.io');
  await page.fill('#password', 'customer123');
  await page.click('#login-btn');
  await expect(page.locator('.alert-success')).toBeVisible();
  await page.context().storageState({ path: 'auth/customer.json' });
});
```

The setup-project advantages are real and worth knowing:

- The setup test appears in the HTML reporter — you can see traces and screenshots if it fails
- The dependency graph is explicit: `chromium` runs only after `setup` passes
- Multiple projects can depend on the same setup project

**But remember the caveat.** This whole approach relies on `storageState` carrying the auth. For **TestMarket Lab's HTTP-only session, the saved `auth/customer.json` will not contain the session cookie**, so dependent tests would start logged out. Reach for the setup-project pattern when your app stores auth in a token/localStorage or a non-HTTP-only cookie; reach for the authenticated fixture above when it uses an HTTP-only session — as our practice app does.

## Multiple roles

Real applications have multiple user roles with different permissions. With the fixture approach, each role is just another fixture — you already saw `customerPage` and `adminPage` above. With the setup-project approach (token/localStorage apps), you write one setup test per role and wire each saved file to its own project:

```ts
// tests/setup/auth.setup.ts  (token/localStorage apps only)
import { test as setup, expect } from '@playwright/test';
import path from 'path';

const authDir = path.join(process.cwd(), 'auth');

setup('authenticate as customer', async ({ page }) => {
  await page.goto('/auth/login');
  await page.fill('#email', 'customer@test.io');
  await page.fill('#password', 'customer123');
  await page.click('#login-btn');
  await expect(page.locator('.alert-success')).toBeVisible();
  await page.context().storageState({ path: path.join(authDir, 'customer.json') });
});

setup('authenticate as admin', async ({ page }) => {
  await page.goto('/auth/login');
  await page.fill('#email', 'admin@test.io');
  await page.fill('#password', 'admin123');
  await page.click('#login-btn');
  await expect(page.locator('.alert-success')).toBeVisible();
  await page.context().storageState({ path: path.join(authDir, 'admin.json') });
});
```

```ts
projects: [
  { name: 'setup', testMatch: /auth\.setup\.ts/ },
  {
    name: 'chromium',
    use: { storageState: 'auth/customer.json' },
    dependencies: ['setup'],
  },
  {
    name: 'admin-chromium',
    use: { storageState: 'auth/admin.json' },
    dependencies: ['setup'],
  },
],
```

Projects without `dependencies` run in parallel. Projects that declare `dependencies` wait for every listed project to finish and pass before they start. If `setup` fails, the dependent projects are skipped — you won't see misleading failures caused by a missing auth file.

## Choosing between the techniques

| Concern | Authenticated fixture | storageState + setup project |
|---|---|---|
| Works with HTTP-only session cookie | **Yes** (cookie stays in a live context) | **No** (cookie is not serialised) |
| Works with token / localStorage auth | Yes | Yes |
| Best for | Session apps, role-switching, local dev | Token apps, large CI suites |
| Config change needed | No | Yes (projects + dependencies) |
| Visible in HTML reporter | Per test | Yes (own setup phase) |
| Multi-role support | One fixture per role | One project per role |
| Login cost | Once per test, or once per worker | Once per suite run |

For **TestMarket Lab**, the left column is the correct choice.

## API login

UI login is convenient but slow (~1–3 seconds). When an app exposes a login API, you can authenticate programmatically and skip the form. The exact mechanics depend on how the app returns auth:

- **Token in the response body** → read it and store it (a cookie or `localStorage` entry), then save `storageState` or set it on a context.
- **Session cookie set by the API** → call the endpoint *from a browser context* so the `Set-Cookie` lands in that context, then keep using the context (a fixture) for the rest of the test.

TestMarket Lab's `POST /api/auth/login` returns user data only (`{ id, email, name, role }`) — **no token** — and it does not establish a browser session, so there is nothing for `storageState` to save from it. It's useful for asserting API behaviour, but for authenticated *UI* tests in this app, stick with the fixture-login pattern above.

When a token-based API *is* available, the speed win is real:

```ts
// Illustrative: only for an app whose /api/auth/login returns a token.
const response = await request.post('http://localhost:3000/api/auth/login', {
  data: { email: 'customer@test.io', password: 'customer123' },
});
expect(response.ok()).toBeTruthy();
const { token } = await response.json();        // exists only on token-based APIs

const context = await browser.newContext();
await context.addInitScript((t) => localStorage.setItem('token', t), token);
await context.storageState({ path: 'auth/customer.json' });
await context.close();
```

**When API login is the right choice:**
- High-volume setups where setup time is measurable in CI
- Applications with long, multi-step UI login flows
- Token-based APIs where the response gives you something `storageState` can keep

**When to stick with UI / fixture login:**
- Server-side session apps with HTTP-only cookies (like TestMarket Lab)
- SSO, OAuth2, or multi-factor flows with no direct API endpoint
- When verifying the actual login UI is part of your coverage

## Security — do not commit real credentials

Saved auth state and credentials are sensitive. Treat them like passwords.

**Add `auth/` to `.gitignore`** (relevant when you do use `storageState` files):

```
# .gitignore
auth/
```

**Use `.env` for credentials, never hard-code them:**

```ts
// .env
CUSTOMER_EMAIL=customer@test.io
CUSTOMER_PASSWORD=customer123
```

```ts
// fixtures/auth.fixture.ts
import 'dotenv/config';

// ...inside the login helper:
await page.fill('#email', process.env.CUSTOMER_EMAIL!);
await page.fill('#password', process.env.CUSTOMER_PASSWORD!);
```

**In CI,** set credentials as encrypted environment variables in your provider (GitHub Actions Secrets, GitLab CI/CD Variables, etc.). If you use `storageState` files, generate them fresh at the start of each pipeline run and never commit `auth/*.json`.

## Exercises

These exercises run against the locally cloned **TestMarket Lab** at `http://localhost:3000` (the app you set up in Module 2). Start it with `npm start` before running tests. Because TestMarket Lab uses an HTTP-only session cookie, every exercise uses the **authenticated-fixture** pattern — not a saved `storageState` file.

### Exercise 1 — Build the auth fixture

Write `tests/starter/fixtures/auth.fixture.ts`. It should export a `test` with two fixtures, `customerPage` and `adminPage`. Each fixture:

1. Creates a new browser context and page
2. Goes to `/auth/login`
3. Fills `#email` and `#password` (customer: `customer@test.io` / `customer123`; admin: `admin@test.io` / `admin123`)
4. Clicks `#login-btn`
5. Waits for the redirect away from `/auth/login`
6. Yields the page with `use(page)`, then closes the context

Remember to `import type { Page } from '@playwright/test';` so the fixture types compile.
