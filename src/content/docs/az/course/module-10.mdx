## Hər testdə login niyə yavaş və qeyri-sabitdir

Çox test dəstləri `beforeEach` bloku ilə başlayır: login səhifəsinə keçid, istifadəçi adı/şifrə doldurma, forma göndərmə. Bu güvənli görünür, amma praktikada iki ciddi problem yaradır.

**Vaxt problemi.** Tipik UI login 1–3 saniyə çəkir. Bunu 50 testlə vurun — paketi işə salmadan əvvəl 2–3 dəqiqəni yalnız loginə sərf edirsiniz. 200 testdə bu yük 10 dəqiqəni keçir.

**Qeyri-sabitlik problemi.** Hər login cəhdi şəbəkəni keçir, forma sahələrini doldurur, yönləndirmələri gözləyir və serverin dar vaxt çərçivəsində cavab verməsindən asılıdır. Bu addımların hər biri müstəqil uğursuz ola bilər. Qeyri-sabit login bir test xətası deyil — amma elə görünür, hər debug sessiyası isə eyni nöqtəyə gəlib çıxır.

Playwright loginin təkrarlanmasının qarşısını almaq üçün iki yol verir: **`storageState`** (doğrulanmış vəziyyəti diskə serialize edib təkrar oxudur) və **doğrulanmış fixture** (yenidən istifadə oluna bilən bir browser context daxilində bir dəfə login edir və daxil olmuş səhifəni hər testə verir). Bu modul hər ikisini öyrədir və — ən vacibi — hər birinin nə vaxt işlədiyini.

## `storageState` konsepsiyası

İstifadəçi brauzer vasitəsilə daxil olduqda server kimlik sübutu geri göndərir — adətən bunlardan biri və ya bir neçəsi:

- `Set-Cookie` cavab başlığı ilə göndərilən **sessiya kuki**
- `localStorage`-da və ya HTTP-only olmayan kukidə saxlanılan **JWT token**
- İkisinin birləşməsi

Playwright-in `storageState`-i bu sübutu iki üst açarlı bir JSON faylına serialize edir:

```json
{
  "cookies": [
    {
      "name": "session",
      "value": "abc123...",
      "domain": "localhost",
      "path": "/"
    }
  ],
  "origins": [
    {
      "origin": "http://localhost:3000",
      "localStorage": [
        { "name": "token", "value": "eyJhbGciOi..." }
      ]
    }
  ]
}
```

**Vəziyyəti saxlamaq** uğurlu logindən sonra edilir:

```ts
await page.context().storageState({ path: 'auth/customer.json' });
```

Diqqət: çağırış `page`-də deyil, `page.context()`-dədir — `storageState` `BrowserContext` metodudur.

**Vəziyyəti yükləmək** yeni context yaradanda edilir (və ya konfiqurasiya vasitəsilə — bu avtomatik edir):

```ts
const context = await browser.newContext({
  storageState: 'auth/customer.json',
});
```

Həmin context-də hər hansı səhifə yüklənmədən əvvəl Playwright fayldan kukiləri və localStorage-ı öncədən doldurur. Tətbiq artıq doğrulanmış bir brauzer görür.

**`storageState` ideal alət olduqda.** O, autentifikasiya əldə edə biləcəyi bir yerdə yaşadıqda parlayır:

- `localStorage`-dakı **JWT (və ya istənilən token)** — `origins` açarı vasitəsilə əldə edilir
- **HTTP-only olmayan kuki** — JavaScript-in `document.cookie` vasitəsilə oxuya bildiyi kuki

Token əsaslı SPA-ların əksəriyyəti bu kateqoriyaya düşür və onlar üçün klassik "bir dəfə daxil ol, `storageState` saxla, hər yerdə yenidən istifadə et" nümunəsi tam doğrudur.

## Tələ: HTTP-only sessiya kukiləri

`storageState` yalnız səhifənin oxuya bildiyini saxlaya bilər: `document.cookie`-yə açıq olan kukilər, üstəgəl `localStorage`/`sessionStorage`. O, `HttpOnly` işarələnmiş bir kukini **saxlaya bilmir**, çünki brauzer həmin kukiləri JavaScript-dən qəsdən gizlədir.

Bu, praktika tətbiqimiz üçün vacibdir. **TestMarket Lab server tərəfli sessiya ilə doğrulayır.** O, `express-session` istifadə edir və onun kukisi (`connect.sid`) defolt olaraq **HTTP-only**-dur. JWT yoxdur və login cavabı heç bir token daşımır — `POST /api/auth/login` yalnız `{ id, email, name, role }` qaytarır.

Nəticə birbaşadır: əgər login edib sonra `page.context().storageState({ path })` çağırsanız, alınan fayl **sessiya kukisini ehtiva etməyəcək**. Həmin vəziyyəti yeni bir context-də yenidən yükləyin — tətbiq sizi sistemdən çıxmış kimi qəbul edir. "Bir dəfə `storageState` saxla" resepti bu cür tətbiq üçün sessiyanı sadəcə daşımır.

> Düzəliş kukini HTTP-only olmayan etmək **deyil** — bu, tətbiqin təhlükəsizliyini testlərə uyğunlaşdırmaq üçün zəiflədərdi. Düzəliş canlı, HTTP-only kukini real bir browser context daxilində saxlayan bir nümunədən istifadə etməkdir: **doğrulanmış fixture**.

Beləliklə, bu modulun qalan hissəsində: `storageState`-i token/localStorage auth üçün doğru alət kimi öyrənin (bu cür tətbiqlərlə *qarşılaşacaqsınız*), amma hər TestMarket Lab tapşırığı üçün **fixture-login** yanaşmasından istifadə edin.

## Doğrulanmış fixture nümunəsi (tətbiqimizin ehtiyacı)

İdeya sadədir: login-i bir `BrowserContext` daxilində **bir dəfə** həyata keçirin, sonra həmin artıq doğrulanmış context-i (və onun səhifəsini) fixture vasitəsilə hər testə verin. HTTP-only sessiya kukisi bütün müddət ərzində həmin context daxilində yaşayır — onu heç vaxt serialize etməyə çalışmırıq, deməli `HttpOnly` bayrağının əhəmiyyəti yoxdur.

```ts
// fixtures/auth.fixture.ts
import { test as base } from '@playwright/test';
import type { Page } from '@playwright/test';

async function login(page: Page, email: string, password: string) {
  await page.goto('/auth/login');
  await page.fill('#email', email);
  await page.fill('#password', password);
  await page.click('#login-btn');
  // The server redirects after login and shows a success flash.
  await page.waitForURL((url) => !url.pathname.startsWith('/auth/login'));
}

type AuthFixtures = {
  customerPage: Page;
  adminPage: Page;
};

export const test = base.extend<AuthFixtures>({
  customerPage: async ({ browser }, use) => {
    const context = await browser.newContext();
    const page = await context.newPage();
    await login(page, 'customer@test.io', 'customer123');
    await use(page);
    await context.close();
  },

  adminPage: async ({ browser }, use) => {
    const context = await browser.newContext();
    const page = await context.newPage();
    await login(page, 'admin@test.io', 'admin123');
    await use(page);
    await context.close();
  },
});
```

Testdə istifadəsi — login kodu yoxdur, sadəcə lazım olan rolu istəyin:

```ts
import { test } from '../fixtures/auth.fixture';
import { expect } from '@playwright/test';

test('logged-in customer sees the profile link', async ({ customerPage }) => {
  await customerPage.goto('/');
  await expect(customerPage.locator('[data-testid="nav-profile"]')).toBeVisible();
});

test('admin can reach the admin panel', async ({ adminPage }) => {
  await adminPage.goto('/admin');
  await expect(adminPage.locator('h1')).toContainText('Admin');
});

test('customer cannot reach the admin panel', async ({ customerPage }) => {
  await customerPage.goto('/admin');
  // No /unauthorized route — the app redirects non-admins to home with a flash error.
  await expect(customerPage).toHaveURL('/');
  await expect(customerPage.locator('[data-testid="flash-error"]')).toBeVisible();
});
```

Burada hər fixture **test-əhatəlidir** (test-scoped): ehtiyacı olan hər test üçün təzə bir context yaradır. Bu təmiz və izolə edilmişdir, amma test başına bir dəfə login edir. Növbəti bölmə login xərcini bütöv bir işçi üzrə necə bölüşdürəcəyinizi göstərir.

### İşçi-əhatəli login (işçi başına bir dəfə login)

Eyni rola ehtiyac duyan çoxlu testiniz varsa, login xərcini test başına deyil, **işçi başına** bir dəfə ödəyin. Fixture-i `{ scope: 'worker' }` ilə işarələyin və onun context-ini yenidən istifadə edin:

```ts
// fixtures/auth.fixture.ts
import { test as base } from '@playwright/test';
import type { Page, BrowserContext } from '@playwright/test';

type WorkerAuthFixtures = {
  customerContext: BrowserContext;
};
type TestAuthFixtures = {
  customerPage: Page;
};

export const test = base.extend<TestAuthFixtures, WorkerAuthFixtures>({
  // One logged-in context per worker process.
  customerContext: [async ({ browser }, use) => {
    const context = await browser.newContext();
    const page = await context.newPage();
    await page.goto('/auth/login');
    await page.fill('#email', 'customer@test.io');
    await page.fill('#password', 'customer123');
    await page.click('#login-btn');
    await page.waitForURL((url) => !url.pathname.startsWith('/auth/login'));
    await page.close();
    await use(context);
    await context.close();
  }, { scope: 'worker' }],

  // A fresh page in the shared authenticated context for each test.
  customerPage: async ({ customerContext }, use) => {
    const page = await customerContext.newPage();
    await use(page);
    await page.close();
  },
});
```

`customerPage`-ə qarşı yazılmış testlər əvvəlki kimi görünür — sadəcə artıq test başına login ödəmirlər. Sessiya kukisi paylaşılan işçi context-i daxilində işçinin bütün ömrü boyu canlı qalır.

## `globalSetup` və setup layihələri haqqında qeyd

Playwright sənədlərində və başqa paketlərdə "bir dəfə login" üçün daha iki yol görəcəksiniz: `globalSetup` funksiyası və digər layihələrin `dependencies` vasitəsilə elan etdiyi xüsusi bir **setup layihəsi**. Hər ikisi login addımını bir dəfə işlədir və sonra `use.storageState`-i saxlanmış fayla yönəldir:

```ts
// playwright.config.ts (storageState-based — works for TOKEN/localStorage apps)
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  projects: [
    { name: 'setup', testMatch: /auth\.setup\.ts/ },
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'], storageState: 'auth/customer.json' },
      dependencies: ['setup'],
    },
  ],
});
```

```ts
// tests/setup/auth.setup.ts
import { test as setup, expect } from '@playwright/test';

setup('authenticate as customer', async ({ page }) => {
  await page.goto('/auth/login');
  await page.fill('#email', 'customer@test.io');
  await page.fill('#password', 'customer123');
  await page.click('#login-btn');
  await expect(page.locator('.alert-success')).toBeVisible();
  await page.context().storageState({ path: 'auth/customer.json' });
});
```

Setup layihəsinin üstünlükləri realdır və bilməyə dəyər:

- Setup testi HTML reporter-da görünür — uğursuz olduqda iz (trace) və skrinşotlara baxa bilərsiniz
- Asılılıq qrafiki açıq-aydındır: `chromium` yalnız `setup` keçdikdən sonra işləyir
- Bir neçə layihə eyni setup layihəsindən asılı ola bilər

**Amma tələni unutmayın.** Bütün bu yanaşma `storageState`-in auth-u daşımasından asılıdır. **TestMarket Lab-ın HTTP-only sessiyası üçün saxlanmış `auth/customer.json` sessiya kukisini ehtiva etməyəcək**, deməli asılı testlər sistemdən çıxmış vəziyyətdə başlayar. Tətbiqiniz auth-u token/localStorage-da və ya HTTP-only olmayan kukidə saxlayırsa, setup layihəsi nümunəsinə müraciət edin; HTTP-only sessiya istifadə edirsə — praktika tətbiqimiz kimi — yuxarıdakı doğrulanmış fixture-ə müraciət edin.

## Çoxsaylı rollar

Real tətbiqlərdə müxtəlif icazələrə malik çoxsaylı istifadəçi rolları var. Fixture yanaşmasında hər rol sadəcə başqa bir fixture-dir — yuxarıda artıq `customerPage` və `adminPage`-i gördünüz. Setup layihəsi yanaşmasında (token/localStorage tətbiqləri) hər rol üçün bir setup testi yazır və hər saxlanmış faylı öz layihəsinə bağlayırsınız:

```ts
// tests/setup/auth.setup.ts  (token/localStorage apps only)
import { test as setup, expect } from '@playwright/test';
import path from 'path';

const authDir = path.join(process.cwd(), 'auth');

setup('authenticate as customer', async ({ page }) => {
  await page.goto('/auth/login');
  await page.fill('#email', 'customer@test.io');
  await page.fill('#password', 'customer123');
  await page.click('#login-btn');
  await expect(page.locator('.alert-success')).toBeVisible();
  await page.context().storageState({ path: path.join(authDir, 'customer.json') });
});

setup('authenticate as admin', async ({ page }) => {
  await page.goto('/auth/login');
  await page.fill('#email', 'admin@test.io');
  await page.fill('#password', 'admin123');
  await page.click('#login-btn');
  await expect(page.locator('.alert-success')).toBeVisible();
  await page.context().storageState({ path: path.join(authDir, 'admin.json') });
});
```

```ts
projects: [
  { name: 'setup', testMatch: /auth\.setup\.ts/ },
  {
    name: 'chromium',
    use: { storageState: 'auth/customer.json' },
    dependencies: ['setup'],
  },
  {
    name: 'admin-chromium',
    use: { storageState: 'auth/admin.json' },
    dependencies: ['setup'],
  },
],
```

`dependencies`-siz layihələr paralel işləyir. `dependencies` elan edən layihələr, siyahıdakı hər layihə bitib keçənə qədər gözləyir. `setup` uğursuz olarsa, asılı layihələr ötürülür — mövcud olmayan auth faylından qaynaqlanan çaşdırıcı uğursuzluqlar görməzsiniz.

## Texnikalar arasında seçim

| Narahatlıq | Doğrulanmış fixture | storageState + setup layihəsi |
|---|---|---|
| HTTP-only sessiya kukisi ilə işləyir | **Bəli** (kuki canlı context-də qalır) | **Xeyr** (kuki serialize edilmir) |
| Token / localStorage auth ilə işləyir | Bəli | Bəli |
| Ən yaxşı olduğu yer | Sessiya tətbiqləri, rol dəyişdirmə, lokal inkişaf | Token tətbiqləri, böyük CI paketləri |
| Konfiqurasiya dəyişikliyi lazımdır | Xeyr | Bəli (layihələr + dependencies) |
| HTML reporter-da görünür | Test başına | Bəli (öz setup fazası) |
| Çox rollara dəstək | Rol başına bir fixture | Rol başına bir layihə |
| Login xərci | Test başına, və ya işçi başına bir dəfə | Paket işləməsi başına bir dəfə |

**TestMarket Lab** üçün doğru seçim sol sütundur.

## API login

UI login rahatdır amma yavaşdır (~1–3 saniyə). Tətbiq bir login API açıqlayırsa, proqramatik olaraq doğrulaya və formanı keçə bilərsiniz. Dəqiq mexanika tətbiqin auth-u necə qaytarmasından asılıdır:

- **Cavab gövdəsində token** → onu oxuyun və saxlayın (bir kuki və ya `localStorage` qeydi), sonra `storageState` saxlayın və ya onu context-də təyin edin.
- **API tərəfindən təyin edilən sessiya kukisi** → endpoint-i *bir browser context-dən* çağırın ki, `Set-Cookie` həmin context-ə düşsün, sonra testin qalan hissəsi üçün context-dən (bir fixture) istifadə etməyə davam edin.

TestMarket Lab-ın `POST /api/auth/login` yalnız istifadəçi məlumatlarını (`{ id, email, name, role }`) qaytarır — **token yoxdur** — və brauzer sessiyası qurmur, deməli `storageState`-in ondan saxlayacağı heç nə yoxdur. O, API davranışını yoxlamaq üçün faydalıdır, amma bu tətbiqdə doğrulanmış *UI* testləri üçün yuxarıdakı fixture-login nümunəsinə sadiq qalın.

Token əsaslı API *mövcud olduqda* sürət qazancı realdır:

```ts
// Illustrative: only for an app whose /api/auth/login returns a token.
const response = await request.post('http://localhost:3000/api/auth/login', {
  data: { email: 'customer@test.io', password: 'customer123' },
});
expect(response.ok()).toBeTruthy();
const { token } = await response.json();        // exists only on token-based APIs

const context = await browser.newContext();
await context.addInitScript((t) => localStorage.setItem('token', t), token);
await context.storageState({ path: 'auth/customer.json' });
await context.close();
```

**API login-in uyğun olduğu hallar:**
- Setup müddətinin CI-da ölçülə biləcəyi yüksək həcmli quraşdırmalar
- Uzun, çox addımlı UI login axınlarına malik tətbiqlər
- Cavabın `storageState`-in saxlaya biləcəyi bir şey verdiyi token əsaslı API-lər

**UI / fixture login-ə sadiq qalmaq lazım olan hallar:**
- HTTP-only kukili server tərəfli sessiya tətbiqləri (TestMarket Lab kimi)
- Birbaşa API endpoint-i olmayan SSO, OAuth2 və ya çox faktorlu axınlar
- Real login UI-nin yoxlanılması əhatənizin bir hissəsi olduqda

## Təhlükəsizlik — real etimadnamələri commit etməyin

Saxlanmış auth vəziyyəti və etimadnamələr həssasdır. Onlara şifrə kimi yanaşın.

**`auth/` qovluğunu `.gitignore`-a əlavə edin** (`storageState` faylları istifadə etdiyiniz hallarda aktualdır):

```
# .gitignore
auth/
```

**Etimadnamələr üçün `.env` istifadə edin, onları heç vaxt kodda yazmayın:**

```ts
// .env
CUSTOMER_EMAIL=customer@test.io
CUSTOMER_PASSWORD=customer123
```

```ts
// fixtures/auth.fixture.ts
import 'dotenv/config';

// ...inside the login helper:
await page.fill('#email', process.env.CUSTOMER_EMAIL!);
await page.fill('#password', process.env.CUSTOMER_PASSWORD!);
```

**CI-da** etimadnamələri provayderinizin şifrəli mühit dəyişənlərində (GitHub Actions Secrets, GitLab CI/CD Variables və s.) təyin edin. `storageState` faylları istifadə edirsinizsə, onları hər pipeline işinin başında təzədən yaradın və `auth/*.json`-ı heç vaxt commit etməyin.

## Tapşırıqlar

Bu tapşırıqlar lokal olaraq klonlanmış **TestMarket Lab** üzərində `http://localhost:3000`-də işləyir (Modul 2-də quraşdırdığınız tətbiq). Testləri işlətməzdən əvvəl onu `npm start` ilə başladın. TestMarket Lab HTTP-only sessiya kukisi istifadə etdiyi üçün hər tapşırıq saxlanmış `storageState` faylını deyil, **doğrulanmış fixture** nümunəsini istifadə edir.

### Tapşırıq 1 — Auth fixture-i qurun

`tests/starter/fixtures/auth.fixture.ts` yazın. O, iki fixture — `customerPage` və `adminPage` — ilə bir `test` ixrac etməlidir. Hər fixture:

1. Yeni bir browser context və səhifə yaradır
2. `/auth/login`-ə keçir
3. `#email` və `#password`-u doldurur (müştəri: `customer@test.io` / `customer123`; admin: `admin@test.io` / `admin123`)
4. `#login-btn`-a klikləyir
5. `/auth/login`-dən kənara yönləndirməni gözləyir
6. `use(page)` ilə səhifəni verir, sonra context-i bağlayır

Fixture tipləri kompilyasiya olunsun deyə `import type { Page } from '@playwright/test';` yazmağı unutmayın.

### Tapşırıq 2 — Doğrulanmış müştəri testi (login kodu yoxdur)

Fixture-inizi istifadə edərək `tests/starter/tests/profile.spec.ts` yaradın:

```ts
import { test } from '../fixtures/auth.fixture';
import { expect } from '@playwright/test';

test('customer sees the profile link', async ({ customerPage }) => {
  await customerPage.goto('/');
  await expect(customerPage.locator('[data-testid="nav-profile"]')).toBeVisible();
});
```

Test gövdəsində `page.fill('#email', ...)` olmamalıdır — login-i fixture həll etdi.

### Tapşırıq 3 — Admin admin panelinə çata bilir

```ts
import { test } from '../fixtures/auth.fixture';
import { expect } from '@playwright/test';

test('admin reaches the admin panel', async ({ adminPage }) => {
  await adminPage.goto('/admin');
  await expect(adminPage.locator('h1')).toContainText('Admin');
});
```

### Tapşırıq 4 — Müştəriyə admin paneli qadağandır

Tətbiqin `/unauthorized` route-u yoxdur. `/admin`-ə daxil olan qeyri-admin `/` (ana səhifə) ünvanına flash xətası ilə yönləndirilir.

```ts
import { test } from '../fixtures/auth.fixture';
import { expect } from '@playwright/test';

test('customer cannot reach the admin panel', async ({ customerPage }) => {
  await customerPage.goto('/admin');
  await expect(customerPage).toHaveURL('/');
  await expect(customerPage.locator('[data-testid="flash-error"]')).toBeVisible();
});
```

### Tapşırıq 5 — Bir UI login testi saxlayın

`@playwright/test`-dən sadə `test` ilə (fixture yox, `storageState` yox) tam brauzer login-i həyata keçirən `tests/starter/tests/login.spec.ts`-i qoruyun. Bu test sizi login formasındakı səssiz pozulmalardan qoruyur:

```ts
import { test, expect } from '@playwright/test';

test('login flow works end-to-end', async ({ page }) => {
  await page.goto('/auth/login');
  await page.fill('#email', 'customer@test.io');
  await page.fill('#password', 'customer123');
  await page.click('#login-btn');
  await expect(page.locator('.alert-success')).toBeVisible();
});
```

### Çətin tapşırıq — İşçi-əhatəli login

`customerPage` fixture-inizi yenidən qurun ki, login test başına deyil, **işçi başına bir dəfə** baş versin (onu "İşçi-əhatəli login" bölməsində göstərildiyi kimi işçi-əhatəli `customerContext` və test-əhatəli `customerPage`-ə bölün). `--workers=1` ilə təsdiqləyin ki, login bir neçə müştəri testi üçün yalnız bir dəfə işləyir.
